成果物：学習記録を用いたGraph RAG

プロジェクト概要

  • 本アプリは、Knowledge GraphとGraph RAGを活用した過去の学習を振り返ることができるWEBアプリケーションです。

機能

  • TopicやRelationshipをLLMを用いて抽出・DB登録
  • 学習した項目または内容・関係性の検索、LLMによる出力
  • 検索方法
    • learning_record：特定のトピックについて、過去に何を学習したかを確認する質問
    • relationship：あるトピックと別のトピックが、どのような関係にあるか確認する質問
    • related_learning_record：特定のトピックそのものではなく、そのトピックに関連する別のトピックを通じて、関連する学習内容を探す質問

技術構成

  • Python
    • LangChain
    • pydantic
    • Neo4j
    • Django
  • LLM
    • ollama：qwen3:1.7b

処理フロー

  1. 質問内容の入力
  2. 検索方法の選択
  3. トピック名の抽出
  4. CypherクエリでNeo4jの検索
  5. LLMにトピック＋関係性＋テキストを入力
  6. 回答

検証設計

登録文書

文書1

Streamlitについて学習した。

Streamlitでは、st.session_stateを利用することで、
画面操作やページの再実行が発生しても値を保持できる。

また、Streamlitの処理を機能ごとに関数へ分割することで、
main()のif文が増えすぎることを防ぎ、コードの可読性や
拡張性を高めることができる。

文書2

BeautifulSoupについて学習した。

BeautifulSoupでは、BeautifulSoup(html_content, 'html.parser')などを利用することで、
複雑なHTMLやXMLの構造を解析（パース）して目的のデータを容易に抽出できる。

また、スクレイピング処理をターゲット領域ごと（例: ヘッダー解析、商品リスト取得、詳細データ整形など）に関数へ分割することで、
1つの関数やメイン処理内にループや条件分岐が増えすぎることを防ぎ、コードの可読性や
拡張性を高めることができる。

回答

No.1 (Streamlitについて何を学習した？)

Streamlitでは、st.session_stateを用いてページの再実行でも値を保持できるようにし、処理を機能ごとに分割することでコードの可読性と拡張性を高める学習がありました。

No.2 (BeautifulSoupについて何を学習した？)

BeautifulSoupは、複雑なHTMLやXMLの構造を解析（パース）し、目的のデータを簡単に抽出できるツールです。特に、`BeautifulSoup(html_content, 'html.parser')`と使用され、データの抽出が容易になります。また、スクレイピング処理を関数やループ・条件分岐の分割で整理することで、コードの可読性と拡張性が向上します。

No.3 (Streamlitとst.session_stateの関係は？)

関連するTopic間の関係が見つかりませんでした。

No.4 (BeautifulSoupとHTML Parsingの関係は？)

BeautifulSoupはHTMLパースを実行するために必要なライブラリであり、その機能はHTML解析に基づいている。つまり、BeautifulSoupはHTMLパースを介してWebページのHTMLデータを処理する。

No.5 (Streamlitと関連するTopicについて何を学習した？)

Streamlitで学習した内容は、**st.session_state** を利用して画面操作やページ再実行でも値を保持できる点と、処理を機能ごとに分割することでコードの可読性や拡張性を高める点です。

考察

今回の評価では、5件の質問のうち3件で期待した検索方法および回答を得ることができた。一方、No.3ではRelationship検索における検索方向の制約、No.5ではLLMによる検索方法の誤分類が確認された。

この結果から、GraphRAGではNeo4jに正しい知識を登録するだけでなく、質問内容に応じて適切な検索方法を選択し、適切な方向からグラフを検索することが回答精度に影響することが確認できた。

また、No.5の結果から、検索方法の選択を誤った場合、最終的なLLMの回答が登録データと矛盾していなくても、質問者が求めている情報とは異なる回答になる可能性があることが分かった。

今後はRelationship検索の方向性や検索方法の分類精度を改善することが課題となる。

課題1：Relationship検索の方向性 現在は、Topic → Relationship → Topicの出方向だけを検索しています。そのため、Streamlit → USES → st.session_stateに対して、st.session_stateとStreamlitの関係は？ と聞くと取得できません。今後、MATCH (t:Topic)-[rel]-(related:Topic)のように双方向を検索対象にする設計を検討できます。

課題2：検索方法の分類精度 No.5で、 期待：related_learning_record 実際：learning_record となりました。つまり、現在のLLMによる検索方法分類には誤分類が発生することがあります。 これは今後の改善候補として、

  • プロンプト改善
  • 質問例の追加
  • 分類条件の明確化
  • 将来的なFunction Calling / Agent化 などが上げられます。
